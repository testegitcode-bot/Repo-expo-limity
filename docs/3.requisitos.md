## 3.2. Requisitos Não-Funcionais

| **ID** | **Descrição** |
| --- | --- |
| RNF001 | A interface web deve ser desenvolvida utilizando a biblioteca **React**. |
| RNF002 | O aplicativo móvel deve ser desenvolvido utilizando o framework **Flutter**, garantindo compatibilidade com Android e iOS. |
| RNF003 | A aplicação web deve se adaptar adequadamente a diferentes tamanhos de tela (responsividade). |
| RNF004 | A geração do roteiro (busca nas APIs externas + cálculo de otimização) não deve ultrapassar **10 segundos**, para não prejudicar a experiência do usuário. |
| RNF005 | A comunicação entre o frontend (Web/Mobile) e o backend deve ser feita exclusivamente via **API RESTful**. |
| RNF006 | O sistema deve utilizar uma camada de cache (Redis) para armazenar rotas e preços consultados com frequência, reduzindo a sobrecarga sobre as APIs de terceiros e a latência de resposta. |

Obs: acrescente mais linhas, se necessário.

## 3.3. Restrições Arquiteturais

As restrições impostas ao projeto que afetam sua arquitetura são:

- O front-end Web deverá ser desenvolvido em **React**;
- O front-end Mobile deverá ser desenvolvido em **Flutter**, garantindo compatibilidade cross-platform com Android e iOS;
- O back-end deverá centralizar toda a regra de negócio e ser consumido exclusivamente por meio de uma **API RESTful**;
- O sistema depende de integrações externas para obter preços de passagens (ex: Amadeus/Skyscanner) e para caracterização de destinos por categoria (ex: "praia", "montanha") via Google Places API;
- O escopo do MVP está restrito a **destinos nacionais**, de forma a reduzir a complexidade combinatória do algoritmo de otimização de custo;
- O MVP não realiza reserva/pagamento diretamente no app — o sistema atua como **redirecionador** para os parceiros (ex: Skyscanner, Booking), de onde recebe comissão (modelo de afiliados/CPA).
