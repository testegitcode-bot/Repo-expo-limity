# 1. Apresentação

O Limity é uma plataforma inteligente de planejamento de viagens (Web e Mobile) que inverte a lógica tradicional do turismo: em vez de o usuário escolher primeiro um destino e depois tentar encaixá-lo no bolso, ele informa o seu orçamento máximo e sua disponibilidade, e o sistema calcula automaticamente o melhor destino, duração e passagem possíveis dentro desse limite.

## 1.1. Problema

Planejar uma viagem hoje é um processo exaustivo. As plataformas de turismo tradicionais (Booking, Decolar, Kayak) seguem um "funil invertido": o usuário pesquisa primeiro um destino desejado — como uma praia ou uma montanha — e só descobre na etapa final de pagamento que o custo total (passagem, hospedagem e passeios) estoura o orçamento que ele realmente tem disponível. Essa quebra de expectativa gera frustração e, com frequência, o abandono da viagem.

A dor do usuário não é a falta de opções de destino — é a falta de opções que sejam **financeiramente compatíveis desde o início da busca**. Isso afeta especialmente viajantes com orçamento definido e pouco tempo para garimpar promoções em dezenas de sites, como universitários, jovens profissionais em escapadas curtas e famílias que já têm um valor exato guardado para a viagem e não podem contrair dívidas.

## 1.2. Objetivos do trabalho

O objetivo geral deste trabalho é apresentar a descrição do projeto arquitetural do Limity, evidenciando as decisões de arquitetura que sustentam a proposta de valor do produto: entregar roteiros de viagem viáveis a partir de um orçamento informado pelo usuário.

Como objetivos específicos, este trabalho busca:

- Detalhar os requisitos funcionais e não funcionais que orientam as decisões arquiteturais do sistema;
- Descrever a arquitetura cliente-servidor adotada, contemplando os clientes Web (React) e Mobile (Flutter) e o backend centralizado, responsável por concentrar a regra de negócio;
- Apresentar os mecanismos de integração com APIs de terceiros (busca de passagens e caracterização de destinos) e a estratégia de cache adotada para atender ao requisito de desempenho (resposta em até 10 segundos);
- Avaliar a arquitetura proposta frente aos atributos de qualidade mais críticos para o produto — desempenho, interoperabilidade e segurança — utilizando o método ATAM.

## 1.3. Definições e Abreviaturas

- **MVP** — Minimum Viable Product (Produto Mínimo Viável)
- **API** — Application Programming Interface
- **REST** — Representational State Transfer
- **JWT** — JSON Web Token
- **CPA** — Custo Por Aquisição (modelo de receita por afiliados)
- **CAC** — Custo de Aquisição de Cliente
- **ATAM** — Architecture Tradeoff Analysis Method
- **RF** — Requisito Funcional
- **RNF** — Requisito Não Funcional
- **SGBD** — Sistema Gerenciador de Banco de Dados
