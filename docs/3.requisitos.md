## 3.2. Requisitos Não-Funcionais

| **ID** | **Descrição** |
| --- | --- |
| RNF001 | A interface web deve ser desenvolvida utilizando a biblioteca **React**. |
| RNF002 | O aplicativo móvel deve ser desenvolvido utilizando o framework **Flutter**, garantindo compatibilidade nativa com Android e iOS. |
| RNF003 | A aplicação web deve ser totalmente responsiva, adaptando-se a resoluções de desktop, tablets e smartphones. |
| RNF004 | A geração dos pacotes (busca nas APIs externas + cálculo de otimização) não deve ultrapassar o tempo limite de **10 segundos**. |
| RNF005 | A comunicação entre o frontend (Web/Mobile) e o backend deve ser feita exclusivamente via **API RESTful** utilizando o formato JSON. |
| RNF006 | O sistema deve utilizar uma camada de cache (**Redis**) para armazenar rotas e preços consultados com frequência, reduzindo custos de API e latência. |
| RNF007 | A autenticação da API deve ser feita utilizando tokens JWT (JSON Web Tokens), garantindo a segurança das rotas privadas. |
| RNF008 | Senhas de usuários devem ser obrigatoriamente criptografadas no banco de dados utilizando algoritmos de hash seguros (ex: **Bcrypt**). |
| RNF009 | O sistema deve estar em conformidade básica com a LGPD, permitindo que o usuário solicite a exclusão permanente de sua conta e dados. |

## 3.3. Restrições Arquiteturais

As restrições impostas ao projeto que afetam sua arquitetura são:

- O front-end Web deverá ser desenvolvido em **React**;
- O front-end Mobile deverá ser desenvolvido em **Flutter**, garantindo compatibilidade cross-platform com Android e iOS;
- O back-end deverá centralizar toda a regra de negócio e ser consumido exclusivamente por meio de uma **API RESTful**;
- O sistema depende de integrações externas para obter preços de passagens (ex: Amadeus/Skyscanner), hospedagem e para caracterização de destinos por categoria (ex: "praia", "montanha") via Google Places API;
- O escopo do MVP está restrito a **destinos nacionais**, de forma a reduzir a complexidade combinatória do algoritmo de otimização de custo e tempo de processamento;
- O MVP não realiza reserva/pagamento diretamente no app — o sistema atua como **redirecionador** para os parceiros (ex: Skyscanner, Booking), de onde recebe comissão (modelo de afiliados/CPA).

## 3.4. Mecanismos Arquiteturais

| **Análise** | **Design** | **Implementação** |
| --- | --- | --- |
| Persistência | Banco de dados relacional | PostgreSQL |
| Front end (Web) | Single Page Application (SPA) | React |
| Front end (Mobile) | Framework cross-platform | Flutter (Dart) |
| Back end | API REST centralizando as regras de negócio | Node.js (Express ou NestJS) |
| Integração | Consumo de APIs externas via REST, com camada de cache | Amadeus/Skyscanner API (voos) e Google Places API (destinos), com cache em Redis |
| Log do sistema | Registro de erros e requisições HTTP | Winston (Node.js) + Morgan |
| Teste de Software | Testes unitários e de integração | Jest (Backend) e React Testing Library (Web) |
| Deploy / Hospedagem | Containers e Cloud Hosting | Docker, hospedado na AWS (EC2/RDS) ou Vercel (Front) + Render/Railway (Back) |
