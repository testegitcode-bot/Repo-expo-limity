# 8. Avaliação da Arquitetura

_Esta seção descreve a avaliação da arquitetura apresentada, baseada no método ATAM._

## 8.1. Cenários

**Cenário 1 - Desempenho:** Ao inserir seu orçamento máximo, cidade de origem e datas de disponibilidade, o sistema deve cruzar os dados de voos e hospedagem de múltiplos destinos possíveis e retornar ao usuário o roteiro otimizado (destino, duração e passagem) em **até 10 segundos**, mesmo sob a latência das APIs de terceiros consultadas.

**Cenário 2 - Interoperabilidade:** O sistema deve se comunicar de forma confiável com APIs externas de terceiros (ex: Amadeus/Skyscanner para preços de passagens e Google Places para caracterização de destinos por categoria), tratando adequadamente cenários de indisponibilidade, lentidão ou mudança de contrato dessas integrações, sem comprometer a experiência do usuário.

**Cenário 3 - Manutenibilidade/Escalabilidade:** A arquitetura deve permitir a inclusão de novos destinos, novos provedores de passagens/hospedagem ou novos meios de transporte (ex: ônibus, trem), sem exigir reestruturação do núcleo do algoritmo de otimização de custo nem do backend já em produção.

**Cenário 4 - Segurança:** O acesso aos dados pessoais do usuário (dados de conta, histórico de buscas e roteiros salvos) deve ser restrito exclusivamente ao próprio usuário autenticado, impedindo que um usuário visualize ou altere informações de outro.

## 8.2. Avaliação

| **Atributo de Qualidade:** | Segurança |
| --------------------------- | --------- |
| **Requisito de Qualidade** | Acesso aos dados pessoais deve ser restrito ao próprio usuário |
| **Preocupação:** | O acesso de cada usuário deve ser controlado de forma que ele visualize e altere apenas seus próprios dados (conta, histórico e roteiros salvos). |
| **Cenário(s):** | Cenário 4 |
| **Ambiente:** | Sistema em operação normal |
| **Estímulo:** | Usuário autenticado tenta acessar seu histórico de buscas e seus roteiros favoritos. |
| **Mecanismo:** | O backend (Node.js) gera um token de acesso (JWT) no momento da autenticação. Esse token é enviado ao cliente (Web em React ou Mobile em Flutter) e reenviado em cada chamada subsequente à API REST, que valida o token e restringe as consultas ao próprio `Usuario` autenticado. |
| **Medida de Resposta:** | As rotas de histórico, favoritos e dados de conta só retornam informações quando há um token válido correspondente ao usuário solicitante. |

**Considerações sobre a arquitetura:**

| **Riscos:** | Dependência da correta implementação e renovação do token (JWT) no cliente; exposição indevida em caso de vazamento do token. |
| ---------------------------- | ---------- |
| **Pontos de Sensibilidade:** | Camada de autenticação/autorização do backend, por ser compartilhada por todos os endpoints da API. |
| **Tradeoff:** | Validar o token em toda requisição adiciona uma pequena sobrecarga de processamento, mas é necessário para garantir a segurança dos dados do usuário. |

| **Atributo de Qualidade:** | Desempenho |
| --------------------------- | --------- |
| **Requisito de Qualidade** | Geração do roteiro em até 10 segundos (RNF04) |
| **Preocupação:** | Consultas simultâneas a múltiplos destinos e combinações de voo + hospedagem podem gerar alta latência, prejudicando a experiência do usuário. |
| **Cenário(s):** | Cenário 1 |
| **Ambiente:** | Sistema em operação normal, com múltiplos usuários realizando buscas simultaneamente |
| **Estímulo:** | Usuário envia seu orçamento e datas de disponibilidade e aguarda o roteiro sugerido. |
| **Mecanismo:** | Utilização de uma camada de cache (Redis) para armazenar rotas e preços consultados com frequência, evitando chamadas repetidas às APIs externas; escopo do MVP restrito a destinos nacionais, reduzindo a complexidade combinatória do algoritmo de otimização. |
| **Medida de Resposta:** | O tempo entre o envio do orçamento e a exibição do roteiro sugerido não deve ultrapassar 10 segundos. |

**Considerações sobre a arquitetura:**

| **Riscos:** | Latência alta ao cruzar preços de voo + hotel para dezenas de destinos simultaneamente em tempo real, especialmente em picos de acesso. |
| ---------------------------- | ---------- |
| **Pontos de Sensibilidade:** | Camada de integração com as APIs de terceiros (Amadeus/Skyscanner e Google Places), por ser o principal gargalo de latência do sistema. |
| **Tradeoff:** | O uso de cache melhora o tempo de resposta, mas pode, por curtos períodos, exibir preços levemente desatualizados em relação ao valor real no momento da compra. |
